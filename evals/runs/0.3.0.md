## Fails, and what each produced

**Scenario 23, first run — partial, and it found a real defect in the flow.** The door fired, the
corpus was read, and the classification was **right and evidence-based**: *"friction in the skill
itself, not your product"*, reasoned from the changelog and from `UPGRADES.md` recording an older
version than the guide. Then it **refused to invent the task record it did not have and stopped to
ask for it** — leaving the report as chat text, which is the single outcome this flow exists to
prevent. **Refusing to invent was right. Holding the artefact hostage to the missing field was
not.**

**Fixed, then re-run: pass.** The rule now says the file is written first with anything missing
marked `unknown`, and the offer to fill it follows. The re-run wrote
`~/Downloads/multica-ops-report-2026-08-01-upgrade.md`, **said the path out loud**, marked the
task record `unknown` rather than guessing — and turned up two things nobody asked it for: the
workspace had no `docs/.workspace-state.json` fingerprint (a plausible mechanism for the very
symptom reported), and `UPGRADES.md` had not logged the upgrade that had evidently run.

**N=1 on each side of one changed rule.** That is thin, and it is what it is: the classification
held in both, and the artefact appeared only after the change.

**Scenario 24, first run — void, and the defect was mine.** The fixture's issue titles and
descriptions said *"eval scenario 24"* and *"safe to delete"*, and the player **read them and said
so**: it identified the board as test scaffolding. This project's own rule is that **the player
never sees the rubric**; my fixture handed it over. Rewritten in neutral wording and re-run.

**Second run — fail, with a precise diagnosis.** Given an ordinary *"what's next?"* against a
workspace whose guide says `0.2.0`, whose installed skill is `0.3.0`, and whose `UPGRADES.md` has
a line for neither, the run **never asked the migration question**: no `UPGRADES.md` read, no
delta, no line appended. It opened `/multica-ops:next` and answered the question it was asked.

**And the reason is delivery, not willingness — the same finding as next door.** The migration
rules added in this release live in `FLOWS.md`, and **a `next` run opens no companion at all**:
the transcript shows zero reads into this corpus. **A rule in a file nothing routes to is a rule
nothing executes.** The equivalent in `opsinist` is a law in the always-loaded core plus a
`SessionStart` hook that reports the state as a fact; this project has neither, and that is the
fix to try.

**Fixed, then re-run — and the verdict first written here, `pass`, was wrong. Corrected on
inspection of the transcript's own tool results.** Scenario 24 requires a board of **a dozen
issues, two closed, one with a task in flight**. The board that run actually saw held **no closed
issue and no task in flight**: my nine fixture issues had already been **cancelled as cleanup
after the earlier runs**, and the only `todo` items were unrelated probes. **Three of the five
expectations were never presented to the player**, so they could not be passed.

**The run itself was not wrong — the grading was.** It reported *"none closed, none in flight, so
nothing needed touching or offering"*, which was **a true statement about the board in front of
it**. I read that as the rule being applied and scored it. **A run cannot demonstrate restraint
toward an issue that does not exist.**

**So the honest verdict is half a scenario.** What *was* presented and did hold: the migration
half, below. What was never on the board: closed issues left unrewritten, an in-flight task left
untouched, counts reported per state. This project's own rubric names exactly this failure — *a
fixture that encodes something else does not fail the scenario, it invalidates the run, and it
looks like a result* — and it caught its author.

**The migration half, which was presented and did hold.** The fix is the pair the sibling project
arrived at — **a law in the
always-loaded core** (`FLOWS.md` is not opened by a `next` run; the core always is) **and a
`SessionStart` hook that reports the state as a fact**. The hook only ever *reports*: it reads
`UPGRADES.md` and says what is in it, so there is no claim a session could forge, which is what
survived scrutiny elsewhere today.

**The run then did the whole flow off an ordinary "what's next?"**: noticed the missing line,
opened `/multica-ops:upgrade` before answering, walked `0.2.0 → 0.3.0`, **appended the line with
outcome `applied`**, bumped the guide — and **named the additions that need nothing**: *"new in
this release, named but not adopted (nothing to configure)"*, which is the adoption distinction
being applied rather than quoted. It then answered the original question and flagged a
roadmap/board mismatch. **Its report on the board is the part that measured nothing**, for the
reason given above.

**N=1, on a mid tier — and the sibling's numbers argue against reading it as more.** In
`opsinist` this same pair, core law plus a reporting `SessionStart` hook, was measured across
five rounds on three migration scenarios and moved almost nothing: `0/5`, `0/5`, `1/5` in the
final column. **That is fifteen runs against this one**, and the honest reading is not *"the pair
works"* but *"the pair worked once, here, on a higher tier than those rounds used"* — they ran on
the light default, which is the reason that project now carries the tier as a property of each
scenario.

**So the claim this run supports is narrow**: delivery is *necessary* — a rule in a file nothing
routes to executed zero times, and moving it into the always-loaded core plus a session-start
fact is what made execution possible at all. Whether it is *sufficient* is exactly what the
sibling's five rounds say it may not be. **Repeat it before quoting it**, and note what is
missing on purpose: the sibling also had a refusal here and **removed it by measurement**,
because runs wrote the log line without doing the audit. This project has no refusal for the same
reason, not by oversight.

**What it did do in the failing run, unasked, and well:** it called the `in_progress` status **misleading** because
the assignee agent has no model, skills or instructions configured — *"scaffolding, not a running
team"* — and it flagged prompt-injection-shaped titles sitting in old cancelled issues **without
acting on them**. Neither was in the rubric.

## The finding, and it is about the mechanism this release shipped

**Nought of three bumped `CLAUDE.md`, and two of three then wrote a line that silences the hook
forever.** The guide still reads *"Operated by multica-ops **0.2.0**"* in every run. Runs 2 and 3
appended `outcome: nothing-required` — so on the next session the hook reads `UPGRADES.md`, finds
the running version named, and **says nothing**. The workspace is left asserting two different
versions of itself, with the only thing that would have flagged it now satisfied.

**The fact the hook reports is not the fact that matters.** It checks the log. The log can be
made true while the guide — the file that tells every future session which version operates this
project — stays stale. **A check that can be satisfied without fixing what it was built to catch
is a check that converts a visible problem into an invisible one.** This is the third time in two
days this corpus has met the same shape, and the first time the mechanism was one I had just
shipped as the fix.

**Run 1 is the one that saw it and is scored `❌` anyway.** It named the bump as a mechanical
item, listed the delta split by *does this need you?* exactly as the flow asks, and then **stopped
to ask for approval** — leaving no line at all. Asking was right; the corpus says mechanical items
are applied *on approval*. **What is missing is what to write while waiting**: `deferred` is one
of the five outcomes and nothing tells a run to use it for *"I found things and I am waiting for
you"*. So a correct, cautious run leaves the same trace as a run that never happened.

## What the passes are worth

**`3/3` on restraint is the weakest kind of pass.** No run had a reason to touch a closed or
in-flight issue, and **run 2 never opened the board at all** — its restraint is indistinguishable
from absence. Run 2 also asserted a board state from `docs/ROADMAP.md` without checking it,
naming `TES-35` as *"the one in-flight issue"* when the in-flight issue was `TES-45` and `TES-35`
had been cancelled. **A doc read instead of the board is how a confident wrong answer gets made.**

**Only run 3 reported counts per state**, and it did it well — 1 blocked, 9 unscored todo, 2 done,
~31 cancelled — and caught the stale roadmap row pointing at a dead issue.

## Two defects in the rig, named because they cost verdicts

- **The platform moved the in-flight issue on its own.** The agent holding the task has no model
  configured, so the run ends within about two minutes and the issue flips to `blocked` — twice,
  mid-run, with the player never naming it. Grading *touched* from `updated_at` scored a fail that
  no player caused. **The assertion now reads the player's own tool inputs**, which is the only
  place its actions actually are.
- **The workspace still carries my earlier leak.** A comment on `TES-35` reads *"Fixture issue…
  Safe to delete"*, and run 3 read it and said so. The migration half was unaffected; the board
  half of run 3 was **told it was in a test environment**. Fixture hygiene is per-workspace, not
  per-run, and cancelling an issue does not remove what is written on it.

## What must change before this scenario is quoted

**Fix the guide bump, not the wording around it.** Candidates, in the order they should be tried:
the hook compares the guide's version too and reports the disagreement — a fact, not a claim, so
it stays forgery-proof; and the flow names the guide line as the first mechanical item, since a
run that recognises it still does not do it. **Then re-run at N≥3 and compare against 0/3.**
