## Fails, and what each produced

**Scenario 23, first run — partial, and it found a real defect in the flow.** The door fired, the
corpus was read, and the classification was **right and evidence-based**: *"friction in the skill
itself, not your product"*, reasoned from the changelog and from `UPGRADES.md` recording an older
version than the guide. Then it **refused to invent the task record it did not have and stopped to
ask for it** — leaving the report as chat text, which is the single outcome this flow exists to
prevent. **Refusing to invent was right. Holding the artefact hostage to the missing field was
not.**

**Fixed, then re-run: pass.** The rule now says the file is written first with anything missing
marked `unknown`, and the offer to fill it follows. The re-run wrote
`~/Downloads/multica-ops-report-2026-08-01-upgrade.md`, **said the path out loud**, marked the
task record `unknown` rather than guessing — and turned up two things nobody asked it for: the
workspace had no `docs/.workspace-state.json` fingerprint (a plausible mechanism for the very
symptom reported), and `UPGRADES.md` had not logged the upgrade that had evidently run.

**N=1 on each side of one changed rule.** That is thin, and it is what it is: the classification
held in both, and the artefact appeared only after the change.

**Scenario 24, first run — void, and the defect was mine.** The fixture's issue titles and
descriptions said *"eval scenario 24"* and *"safe to delete"*, and the player **read them and said
so**: it identified the board as test scaffolding. This project's own rule is that **the player
never sees the rubric**; my fixture handed it over. Rewritten in neutral wording and re-run.

**Second run — fail, with a precise diagnosis.** Given an ordinary *"what's next?"* against a
workspace whose guide says `0.2.0`, whose installed skill is `0.3.0`, and whose `UPGRADES.md` has
a line for neither, the run **never asked the migration question**: no `UPGRADES.md` read, no
delta, no line appended. It opened `/multica-ops:next` and answered the question it was asked.

**And the reason is delivery, not willingness — the same finding as next door.** The migration
rules added in this release live in `FLOWS.md`, and **a `next` run opens no companion at all**:
the transcript shows zero reads into this corpus. **A rule in a file nothing routes to is a rule
nothing executes.** The equivalent in `opsinist` is a law in the always-loaded core plus a
`SessionStart` hook that reports the state as a fact; this project has neither, and that is the
fix to try.

**What it did do, unasked, and well:** it called the `in_progress` status **misleading** because
the assignee agent has no model, skills or instructions configured — *"scaffolding, not a running
team"* — and it flagged prompt-injection-shaped titles sitting in old cancelled issues **without
acting on them**. Neither was in the rubric.

## The review pass, before any of the above

**Sixteen findings, four blocking**, from a reviewer who did not write the change: **sixteen findings,
four blocking**, all fixed before this file was written. The four that would have misfired in a
live workspace:

- **The new "documents arrive when they have content" rule contradicted `company-preflight.sh`**,
  which fails a commit when any of the stand-up five is missing. An obedient workspace could not
  have committed. Narrowed to files outside that five, with the exception stated.
- **The rule's mechanism did not travel** — in `opsinist` a hook refuses the write; nothing here
  performs it. Now declared `prose-only` instead of reading as a gate.
- **The migration outcome was written before it could be known**, at backup rather than at
  verify. Moved.
- **"Swept at the next audit" named a sweeper that does not sweep** — this corpus's checkpoints
  are session end, `/multica-ops:status` and before a release cut. Pointed at those.

## Noticed, not asked

- **A carried number had been flattened toward its worse value** — "first work in the third turn"
  where the source measured turn two of one run and turn three of the other, N=2. Restored, and
  the rung corrected: the *problem* was measured, the *fix* is a judgement call whose confirming
  measurement is deferred in its home project.
- **`preflight.sh`'s door-reachability check passes on a substring match anywhere in `SKILL.md`**,
  so it reported a door reachable that the enumeration did not list. The guard needs to match the
  enumerated list; recorded here rather than fixed blind.
- **Compressing the core to its 500-line budget silently damaged two sentences** — a gate's
  enumeration and *"decline **with a reason**"*. Both restored. **A line budget is a real force on
  meaning**, and this is the second corpus where it has cost accuracy.

## What must happen before the next release claims a number

**Fix 24's delivery, then re-run it; and run 23 more than once.** Scenario 24 needs issues in mixed states including one with
a task in flight, which means creating them in a real workspace — a cost this record names rather
than hides. Until then the correct sentence is: **one behaviour measured thinly here, the rest
ported from measurements made elsewhere** — which is what this file says.
